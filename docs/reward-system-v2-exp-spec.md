# 보상 시스템 v2 — EXP 이코노미 설계

> 작성일: 2026-04-19
> **Single Source of Truth**: 모든 수치는 `src/data/levelSystemData.js`에 정의.
> 이 문서는 **왜 그렇게 설계했는지**와 **어떤 규칙으로 적용되는지**만 서술한다.
> 수치가 바뀌면 데이터 파일을 수정하고 이 문서는 건드리지 않는다.

---

## 0. 설계 원칙

1. **두 축 보상** — 피드(자랑) / 배틀(큐레이션)은 서로 다른 심리를 자극하므로 보상 체계를 분리한다
2. **완성도 유도** — 대충 쓴 글과 꼼꼼히 쓴 글의 EXP가 2배 이상 차이 나야 한다
3. **일일 캡** — 반응 수신 EXP에 상한을 둬서 상위 유저 독식과 품앗이 어뷰징을 막는다
4. **중위권 보상** — 배틀 TOP 50, 참여 완주 보상 등으로 중간층에게도 동기를 준다
5. **레벨 체감 곡선** — Plain 구간은 하루 안에 레벨업, 후반은 장기 목표가 되도록 비선형 설계

## 2. EXP 적용 규칙 (데이터만 봐서는 모르는 로직)

### 2.1 인증 작성 — 보너스 판정 시점

인증이 **서버에 PUBLISH된 시점**에 한 번 계산. 추후 수정으로 조건을 채워도 보너스를 **소급 적용하지 않는다** (어뷰징 방지).

- `review.length >= 50` → 화이트스페이스 제외 길이 기준
- `attachmentFiles.length >= 3` → 썸네일 처리된 최종 저장본 기준
- `buyPlace` → `"모름"`, 공백, null 은 제외
- `buyPrice` → 숫자 > 0. 단 `"선물받음"` 플래그는 포함(0원이어도 인정)
- `hashtags.length >= 3` → 중복 제거 후 카운트

모든 조건 충족 시 **130 EXP** (기본 60 + 보너스 70).

### 2.2 반응 수신 — 일일 캡 (수신자 기준)

- 캡은 **수신자의 UTC+9 자정 기준 하루** 동안 쌓인 EXP를 기준으로 한다
- 캡 도달 후 들어온 반응은 뱃지 진행도·🔥 카운트에만 반영되고 EXP는 0
- **글 단위가 아니라 유저 단위**로 캡 적용 (한 글이 터져서 혼자 먹어도 합산)

### 2.3 배틀 — 가중 투표 vs 단순 투표

- **가중 투표**: 1st/2nd/3rd를 **모두** 선택했을 때만 가중으로 인정. 하나라도 비면 단순 투표 EXP 처리
- 동일 배틀에 재투표해도 EXP는 1회만 지급

### 2.4 PICK 한마디

- **20자 이상** (공백 제외) 작성 시에만 EXP 지급
- 동일 배틀 내 여러 번 수정해도 EXP는 1회
- 👍 수신 EXP는 캡 내에서 누적 (`EXP_RULES.battle` 마지막 항목)

### 2.5 HOT 100 발굴자

- 제품별 **최초 인증자 1인**에게만 귀속
- 해당 제품이 HOT 랭킹에 진입하는 순간 이벤트 발화
- TOP 100 → TOP 50 → TOP 10 순으로 누적 지급 (같은 제품으로 세 번 다 받을 수 있음)
- 🏅 발굴자 뱃지는 TOP 10 진입 누적 5회 달성 시 부여

### 2.6 예측 적중

- 배틀 종료 시점, 유저의 **1st 선택**이 실제 1위와 일치하면 발화
- 카테고리별 적중률은 누적되어 프로필에 노출 (예: "스니커즈 예측 정확도 68%")

### 2.7 스트릭

- 기준은 **"인증 작성일"**. 반응/투표는 스트릭에 기여하지 않는다
- 자정(KST) 넘어가면 카운트 리셋
- 복구 티켓: 7일 연속 달성 시 1장 지급, 최대 5장 보유. 놓친 다음 날에만 사용 가능

## 3. 레벨 구간 설계 의도

`LEVEL_EXP_TABLE`의 수치는 아래 체감을 만들기 위해 계산되었다:

| 구간 | 체감 목표 | 필요치 설계 |
|---|---|---|
| Plain (1→5) | "가입하자마자 뭔가 되고 있다" | 500 이하 계단식, 첫날 레벨 3–4 도달 가능 |
| Plain→Fruity (5→6) | "첫 등급업 축하" 이벤트 | 800 — 활성 유저 ~4일 |
| Fruity (6→15) | "본격적으로 취향 쌓는 시기" | 선형 1k→3k, 약 1.5개월 |
| Granola (16→25) | "전문성 구간, 속도 점진 둔화" | 4k→18k, 활성 ~6개월까지 |
| Parfait (26→35) | "인플루언서 레이어, 장기 목표" | 20k→40k, 활성 ~1.5년 |
| Signature (36+) | "커뮤니티 상징, 희소성" | 45k+, 하드코어도 10개월 이상 |

> 수치 조정이 필요하면 `LEVEL_EXP_TABLE`만 수정. 표를 이 문서에 다시 적지 않는다.

## 4. 유저 타입별 일일 EXP 예산 (설계 가정)

레벨 테이블을 검증할 때 기준으로 쓴 **이론 상한**. 실측이 아니다.

- **하드코어 (상위 5%)** — 약 1,500 EXP/일 (인증 2개 완성도 MAX, 반응 캡 대부분 소진, 미션 올클리어, 배틀 가중 투표 3회+)
- **활성 유저 (상위 20%)** — 약 550 EXP/일 (인증 1개 80% 완성도, 반응 절반 수준, 미션 2/3)
- **캐주얼 (60%)** — 약 100 EXP/일 (격일 인증, 반응 소량, 미션 1개, 출석)
- **잠수 (20%)** — 약 15 EXP/일 (출석 + 가끔 투표)

→ 레벨 커브가 이 분포에 맞게 설계됨. 실제 지표가 이 가정과 크게 벗어나면 `LEVEL_EXP_TABLE`을 재조정한다.

## 5. v1 → v2 변경 요지

| 영역 | v1 | v2 | 이유 |
|---|---|---|---|
| 인증 EXP | 고정 50 | 60 + 최대 +70 보너스 | 완성도 유도 |
| 🔥 / 👍 수신 | 무제한 | 일일 캡 도입 | 양극화·품앗이 차단 |
| 배틀 우승 | 1,000 | 600 | 양극화 완화 |
| 가중 투표 | 단순과 동일 | 단순의 2.4배 | 숙고 보상 |
| PICK 한마디 | 없음 | 작성/수신 EXP 신설 | 배틀의 바이럴 레버 |
| 저장·공유 당하기 | 없음 | 신설 (각 12, 15) | 자랑 성공의 품질 신호 |
| 배틀 참여/TOP50 | 없음 | 신설 (30, 150) | 중위권 동기 부여 |
| 예측 적중 | 없음 | 신설 (100) | 투표를 "안목 게임"으로 격상 |
| 레벨 테이블 | 20레벨 | 40레벨, 5등급 × 5랭크컬러 | 장기 리텐션 |

## 6. 구현 체크리스트 (Phase 1)

백엔드 붙일 때 만들어야 할 엔드포인트:

1. `POST /api/rewards/exp/feed-create` — 완성도 판정 + EXP 지급 (규칙 2.1)
2. `POST /api/rewards/exp/reaction` — 일일 캡 체크 후 지급 (규칙 2.2)
3. `POST /api/rewards/exp/battle-vote` — 가중/단순 구분 (규칙 2.3)
4. `POST /api/rewards/exp/pick-comment` — 20자 판정, 👍 캡 (규칙 2.4)
5. `GET /api/rewards/daily-cap` — 각 캡 소진 현황 조회 (UI 표시용)
6. `POST /api/rewards/exp/discover` — HOT 랭킹 진입 이벤트 (규칙 2.5)
7. `POST /api/rewards/exp/prediction` — 배틀 종료 시 1st 일치 검사 (규칙 2.6)
8. 배치: 스트릭 롤오버(자정), 주간 랭킹 집계(월요일)

현재 프론트는 `src/api/rewardsApi.js`의 `USE_MOCK = true`로 mock 동작 중. 위 엔드포인트가 나오면 해당 파일 상단 주석 절차대로 스위칭.
